# 12 · Background Tasks：后台任务

前十一章的 Agent，工具调用是**同步**的：模型发起一次调用，整个循环停在那里等结果，`await` 结束才继续。第九章的 `spawn_subagent` 一次研究要二三十秒——两个相互独立的研究串行执行就是将近一分钟，而等待期间 Agent 什么都不能做。真实世界的长任务（构建、测试、数据处理）更是如此。

本章引入后台任务：**`run_in_background` 启动任务后立即返回一个 task id，任务在后台并行执行；完成时，结果作为通知自动注入消息历史**。模型的等待时间从"任务时长"变成"零"。

## 关键认识：把"等待"从循环里拿掉

同步工具调用的本质，是"请求 → 等待 → 观察"三步绑死在同一个 step 里。后台任务把它拆成两半：

```
请求  →  立即返回 task id（Observation：任务已启动，正在运行）
完成  →  结果作为通知，在之后的某个 step 注入消息历史
```

模型的世界观因此发生了一个微妙的变化：**Observation 不再只来自"上一步的 Action"，也可能来自"几步之前启动的后台任务"**。消息历史里多了一类不是模型主动索取的消息——这正是后台任务和前面所有工具的本质区别。

## 三个工具 + 一个注入点

实现由两部分组成：

`tasks.ts` 里的三个工具，走普通的注册、调用、Observation 通道：

- `run_in_background(tool, args)`：启动任务，**立即**返回 `{ task_id, status: "running" }`
- `check_task(task_id)`：按 id 查状态和结果——兜底用的主动轮询
- `list_tasks()`：列出所有任务的 id、工具、状态

`agent.ts` 里的一个注入点：每一步 LLM 请求之前，主循环调用 `taskManager.drainFinished()`，把"已完成但还没通知过"的任务结果作为 user 消息 push 进消息历史。`TaskManager` 用一个 `notified` 集合保证**每条完成通知只进历史一次**。

## 为什么通知优于轮询

一个更省事的设计是：只给 `check_task`，让模型自己轮询。本章故意多做了一个注入点，因为轮询把时序问题甩给了模型——每查一次就是一次 LLM 往返，查早了浪费 token，查晚了拖延答案，而"什么时候该查"本来就是模型不该操心的工程问题。通知把这个问题从模型身上彻底拿掉：**完成事件在下一个 step 自然出现，模型只需要"读到就用"**。`check_task` 保留为逃生舱，对应"我现在就必须知道结果才能决定下一步"的场景。（本章的实测很有意思：模型确实两条路都用了——通知注入之外，它还会主动 `check_task` 确认。）

## 后台任务的上下文：隔离

`TaskManager.start` 为每个后台任务 `new` 一个独立的 `ToolContext`——第九章子代理的同一个先例。两个理由：任务之间互不可见；**避免后台任务与前台并发写同一个 notes / todos 的竞态**。Node 是单线程的，但 `await` 让多个任务的执行交错进行，共享可变状态在交错下照样会乱。隔离一次 `new` 就解决了，这是系列里反复兑现的同一个结构。

## 权限：后台是 safe 工具的专属通道

本章最重要的安全设计藏在 `run_in_background` 的实现里。它本身在 `permission.ts` 里定级 safe，但它是一个**代执行工具**——真正被执行的是它参数里的那个工具。如果不做检查，`run_in_background` 就成了第四章权限系统的后门：前台调用 `save_note` 要审批，后台包一层就绕过了。

所以 `run_in_background` 在启动前会再查一次策略：**只有 `safe` 工具允许进后台**。理由是第四章审批模型的自然推论——审批依赖"人正坐在终端前"，而后台任务完成时人不一定在，一个挂在后台 Promise 里的审批 prompt 会把整个 run 卡死。`sensitive` / `dangerous` 工具只能走前台，在那里审批钩子能正常工作。白名单思维的延伸：**代执行工具必须把内部工具的风险等级重新过一遍策略**。

## 本章的演示任务

`main.ts` 的任务是精心设计的——两个相互独立的慢任务（适合后台）加一个快任务（等待期间顺手做）：

```
1. 用 run_in_background 并行派两个 researcher 子代理，
   分别研究 "ReAct pattern" 和 "tool calling"
2. 等它们跑的时候，用 calculator 算 123 × 456
3. 两个研究结论到达后，连同计算结果一起汇总
```

## 运行

```bash
npx tsx 12BackgroundTasks/main.ts
```

观察点：

- **并行的收益**：实测两个后台子代理各跑约 23 秒，整个 run 约 49 秒；串行 `spawn_subagent` 两次仅子代理就要 46 秒以上，还要外加额外的步骤开销
- **模型在等待期间做了什么**：启动两个后台任务之后，它没有干等，而是顺手完成了计算
- **通知与轮询**：注意 `[Background task finished]` 消息何时出现在消息流里，以及模型什么时候选择主动 `check_task`

值得做的对照实验：

- **把 Background Tasks 提示词分节删掉再跑**：观察模型还会不会想到用 `run_in_background`，还是退回串行 `spawn_subagent`
- **让模型后台执行 `save_note`**：观察它被"只有 safe 工具能进后台"拒绝后，会不会改为前台直接调用（这时审批钩子会正常弹出来）

## 它的边界

- **通知只在 step 边界注入**。如果模型在某个 step 直接返回最终答案，那之后完成的任务通知永远进不了历史——run 结束时仍在 `running` 的任务被静默遗弃，没有取消、没有等待、没有交代
- **没有取消机制**。任务一旦启动就只能跑到完；真实系统需要 `stop_task`（以及"怎么取消一个已经在 await 的 Promise"这个不那么愉快的问题）
- **没有并发上限**。模型可以一口气启动一百个后台任务，对 API 限流（第十一章的 429）和本地资源都是冲击
- **通知是一条普通 user 消息**。第八章的压缩不区分消息来源，通知可能被压进摘要——摘要的四要素保住了数据，但"这是后台任务的结果"这个时序语义丢了

## 动手练习

1. **取消任务**：给 `TaskManager` 加 `stop(task_id)` 和一个 `stop_task` 工具（定级 `sensitive`）。`running` 状态的任务置为 `cancelled`，`drainFinished` 照常通知。思考：已经在 `await` 的 Promise 无法真正取消，`stop` 实际做到的是什么？（提示：标记 + 忽略结果）

2. **并发上限**：给 `TaskManager` 加 `maxConcurrent`（比如 2），超出的任务进入 `queued` 状态排队，有任务完成时按序启动。观察模型收到"任务排队中"的 Observation 后行为是否依然正确。

3. **run 结束时的善后**：`agent.run` 返回答案时如果还有 `running` 的任务，三种策略——等待它们完成、全部取消、直接遗弃——各适用于什么场景？选一种实现，并在 `onRunEnd` 钩子里报告被遗弃的任务。
