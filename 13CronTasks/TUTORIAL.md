# 13 · Cron Tasks：定时任务

第十二章把"等待"从循环里拿掉了，但后台任务的触发源仍然是**这次对话里的需求**——模型决定现在启动，任务马上开跑。还有一类需求的触发源不是对话，是**时间本身**："每天早上九点提醒我开站会"、"每小时检查一次构建"。本章给 Agent 加上 cron：模型用 `create_cron` 把一段 prompt 挂到时间表上，调度器到点就把这段 prompt 作为一次**全新的 run** 跑起来。

## 关键认识：cron 在主循环之外

对比第十二章会发现一个有趣的不对称：后台任务必须改 `agent.ts`——完成通知要注入进行中的那次 run 的消息历史；而 cron **一行 `agent.ts` 都不用改**，因为每次触发不是"往对话里塞消息"，而是从外面发起一次普通的 `agent.run`。

```
后台任务：对话内的并行 → 结果回到这条对话里 → 改循环
cron 任务：对话外的调度 → 每次触发是一条新对话 → 循环不变
```

Agent 不知道自己被调度，就像它不知道终端那头坐着谁。**触发源换了，入口不变**——`agent.run(question)` 这个唯一入口从第一章到现在，承接了人、子代理、后台通知和定时器四种触发源。

## cron 表达式：五字段语法

采用标准 5 字段：`minute hour day-of-month month day-of-week`，每个字段支持 `*`（任意）、`*/n`（每 n）、单值、区间 `a-b`、区间带步长 `a-b/n`、逗号列表。`cron.ts` 里的解析器把每个字段编译成一个"允许值的集合"（`*` 编译成 null 通配），匹配就是五次集合查询。

求"下一次触发时间"用的是最笨也最可靠的办法：**从下一分钟开始逐分钟扫描**，一年为限。一年内扫不到触发时间的表达式（如 `0 0 31 2 *`——2 月没有 31 日）在 `create_cron` 时就会被拒绝，而不是挂在那里永远不响。**创建即校验**：`add()` 里第一件事就是算 `nextFireAt`，非法表达式根本进不了任务表。

## 调度器：tick → 入队 → 串行执行

`CronManager` 的结构只有三层：

1. **tick**：`setInterval` 每秒扫一次任务表，把 `nextFireAt` 已到点的任务挑出来
2. **入队**：到点任务推进一个先进先出队列；recurring 任务顺手重算下一次触发时间，one-shot 任务（`recurring: false`）触发即自动删除
3. **串行 drain**：队列里的触发逐个执行，每次触发是一次完整的 `agent.run`

为什么串行而不是并发？设想一次 run 跑了 70 秒，而任务是"每分钟触发"——如果到点就并发开跑，两个 run 会同时操作共享的 hooks 输出和 `memory.json`，互相踩。串行加队列是**coalescing 的最小实现**：慢的时候触发会排队，但不会丢、不会撞。

## 每次触发是一次全新的 run

这是本章最重要的语义，和第九章子代理是同一个"信息瓶颈"：触发的 prompt 在一个**全新的消息历史**里运行，看不到创建它的那次对话。模型在 `create_cron` 时写的 prompt 就是那个未来 run 的唯一输入，所以提示词规则第 3 条把这点写死：

```
Each fire is a FRESH run that cannot see this
conversation. Write the prompt so it is fully
self-contained.
```

"提醒我喝水"是自包含的；"提醒我刚才说的那件事"不是——到点触发时，"刚才说的那件事"已经不存在了。

## 本章的演示任务

`main.ts` 先跑一次普通对话，让模型自己创建定时任务，然后调度器保持运行：

```
RUN：帮我设置一个定时任务：每分钟提醒我站起来活动一下、喝口水（recurring）
     ↓ 模型调用 create_cron，返回任务 id 和下一次触发时间
（进程不退出，调度器每秒 tick）
     ↓ 到点：CRON FIRED —— agent.run("提醒用户站起来活动一下、喝口水")
     ↓ 一分钟后：再次触发
     ↓ 演示满 2 次触发后停止调度器，退出
```

## 运行

```bash
npx tsx 13CronTasks/main.ts
```

观察点：

- **创建即校验**：模型返回的 Observation 里直接带着 `next_fire_at`——下一次触发时间在创建时就是确定的
- **触发的 prompt 是谁写的**：注意 `CRON FIRED` 日志里的 prompt 文本——它是模型在 RUN 里自己拟的，决定了每次触发时 Agent 会做什么
- **全新 run 的代价**：每次触发都重新打印 system prompt、从零开始消息历史——调度是昂贵的，prompt 该多具体是值得设计的

值得做的对照实验：

- **把 cron 表达式改成非法的**（比如让模型创建 `99 * * * *`）：观察错误 Observation 如何让模型自己修正表达式
- **让模型先 `list_crons` 再决定**：问"我现在有哪些定时任务？"——它应该查到刚才创建的那个
- **用 `delete_cron` 取消**：注意它定级 sensitive，审批钩子会弹出确认——删除是不可逆的取消

## 它的边界

- **进程活着才触发**。任务表在内存里，进程退出，定时任务全部消失；真实系统会把任务持久化，重启后恢复，并补偿停机期间错过的触发
- **分钟是粒度下限**。逐分钟扫描意味着"每 30 秒"这类需求表达不了——这不是扫描算法的限制，是 cron 语法本身的限制
- **dom/dow 用 AND 语义**。标准 cron 在两个字段都受限时用 OR（"每月 1 日**或**每周五"），本章用 AND——语义更直观，但与系统 crontab 的行为不一致，移植表达式时要注意
- **没有 jitter**。"每分钟触发"的任务天然对齐到整分钟边界；如果一万个用户都设 `0 9 * * *`，九点钟 API 会收到一万个同时的请求——真实调度系统会给触发时间加随机抖动
- **错过即跳过**。tick 间隔是 1 秒，但如果一次 run 卡住很久，期间的触发只是排队，不会"补跑 N 次"——这是设计选择，但用户需要知道

## 动手练习

1. **持久化**：把任务表落盘到 `cron.json`（每次 add/remove 后写回），启动时恢复。然后回答最难的那一问：进程停机期间错过的触发怎么办——补跑一次、补跑 N 次、还是直接跳过？参考第十章 `memory.ts` 的持久化方式。

2. **错过补偿**：实现"唤醒时补跑一次"策略——启动时若发现某任务的 `nextFireAt` 在过去，立即触发一次再重排。和练习 1 的持久化配合，进程重启就不再丢任务。

3. **防 herd 抖动**：给 recurring 任务的重排加确定性抖动（比如按任务 id 哈希偏移 0–30 秒），让整点对齐的触发被打散。观察 `next_fire_at` 的变化，想想为什么抖动要"确定"而不是每次随机。
