# 10 · Memory：跨运行的长期记忆

前九章搭出来的 Agent 有一个共同的宿命：**进程一退出，它就失忆**。消息历史、notes、todos 全都活在内存里，随单次运行消亡：第二章的 `ToolContext` 是 `new Agent()` 时创建的 Map，第八章的压缩甚至主动丢弃历史。用户告诉过 Agent"我对花生过敏"，下次运行它一无所知。

本章给 Agent 加上长期记忆：**一个持久化到文件的记忆库，配上 `save_memory` / `search_memory` 两个工具**，让"这次运行学到的事"在"下次运行"还能被捞回来。

## 关键认识：两种记忆，两个时间尺度

到这一章，Agent 身上其实有两类记忆，分工由"信息的寿命"决定：

| | 工作记忆 | 长期记忆 |
|---|---|---|
| 载体 | 消息历史、notes、todos | memory.json 文件 |
| 寿命 | 单次运行 / 单进程 | 跨运行、跨进程 |
| 装什么 | 当前任务的中间状态 | 用户的稳定事实 |
| 满了怎么办 | 第八章：压缩 | 本章：检索（见下） |

判断标准只有一条：**这条信息下次运行还有用吗？** 有用才进长期记忆："用户对花生过敏"明年还有用；"当前 todo 进行到第 2 步"明天就是垃圾。所以系统提示词的 Memory 分节把这条写成硬规则：

```
save_memory: record STABLE facts about the user.
Never save transient task state — that is what notes
and todos are for.
```

不加这条，模型会把任务中间结果也写进记忆，记忆库迅速被一次性信息淹没。**记忆系统的质量首先取决于写入纪律，其次才是检索技术**。

## 记忆 = 一个文件 + 两个工具

`memory.ts` 的实现没有任何新机制：`MemoryStore` 在构造时从 JSON 文件加载，每次 `save` 后整个数组写回磁盘；`search` 是第二章 `knowledge_search` 同款的关键词打分。两个工具走普通的注册、调用、Observation 通道，循环、钩子、压缩、子代理全部零改动。这已经是系列里第四次印证同一个结构：**Agent 的扩展点在工具接口上**。

新增的只有那句 `writeFileSync`：notes 和 memory 的代码长得几乎一样，差别只在"写入即落盘"。**可就这一步，差别是类别上的**：信息第一次活过了产生它的那次运行。

## 检索而非全量注入

一个诱人的替代设计是：启动时把所有记忆塞进系统提示词的 Runtime Context 分节，模型随时可见，省一次工具调用。本章故意不这么做，原因和第七章 skill 不内联全文、第八章不无限保留历史是同一个：**提示词是最贵的地段**。记忆库只会越积越多，全量注入意味着每次 LLM 请求都为全部记忆付费，无关记忆还会稀释注意力。按需检索则把成本收敛到"本次任务真正相关的几条"。

代价是模型得先想到要搜，才搜得到。所以提示词第 2 条专门对抗"不知道自己不知道"：

```
when the user's request may depend on something they told
you in a PREVIOUS run, search memory first instead of
claiming you do not know.
```

## 写入是敏感操作

`permission.ts` 里 `save_memory` 被定为 `sensitive`，走第四章的人工审批，和 `save_note` 同级，但理由更重：写错的 note 只污染本次运行，**写错的记忆会污染未来每一次运行**，而且本章没有实现"遗忘"，写入就是永久。审批钩子在这里拦的不只是危险动作，也是记忆库的质量入口。

## 本章的演示任务

`main.ts` 连续跑两次 `agent.run`：

```
RUN 1：请记住关于我的三件事：
       我的猫叫年糕，生日是 2022 年 3 月 15 日；我对花生过敏；我住在上海
RUN 2：我的猫叫什么名字、生日是哪天？
       我想给它办个生日会，结合我的情况，推荐两款我也能吃的零食
```

`run()` 每次都会新建消息数组，RUN 2 对 RUN 1 的对话内容一行也看不到。它能答出"年糕"和"花生过敏"的唯一途径，是调用 `search_memory` 从 `memory.json` 里捞回来。RUN 2 的"推荐我也能吃的零食"是精心设计的：**它要求模型把检索到的事实（花生过敏）用在推理里**，而不是复述记忆。

## 运行

```bash
npx tsx 10Memory/main.ts
```

观察 RUN 2 的第一步：模型应该在回答前先发起 `search_memory`。值得做的对照实验：

- **跑完后删掉 `memory.json`，注释掉 RUN 1 再跑**：RUN 2 应该搜不到东西，观察它是老实说"没有相关记忆"还是开始编，体会检索工具对幻觉的抑制作用
- **把提示词 Memory 分节的第 2 条删掉再跑**：观察模型在"不知道自己不知道"时会不会主动搜记忆
- **再跑一次完整演示**：注意记忆库里出现了重复的三条事实，本章没有去重机制，这正是练习 1 要解决的

## 它的边界

- **关键词检索很脆弱**。"年糕"能搜到，"我的宠物"就未必。本章的实测里还出现了更典型的一幕：模型用"我的猫名字和生日"做查询，整句因为没有空格被当成一个词，什么都没搜到，换成"猫"才命中。真实系统的记忆检索用 embedding 向量相似度，本章的关键词打分只是把"检索"这个概念讲清楚的最小实现
- **只有写入和读取，没有更新和遗忘**。事实会变（"我搬到了北京"），记忆库只会越堆越厚，旧事实和新事实并存且互相矛盾。一个最小的修法是让 `save_memory` 支持按 id 覆写，但"哪条该被覆写"又需要模型做判断，记忆管理本身就是一个 agent 任务
- **记忆是隐私的集中地**。持久化文件把用户散落的偏好汇成了一幅画像，文件该放哪、谁能读、怎么删，在真实系统里是和功能同等重要的设计题

## 动手练习

1. **遗忘与更新**：给 `MemoryStore` 加 `update_memory(id, content)` 和 `forget_memory(id)` 两个工具（`forget_memory` 定级 dangerous）。改造演示：RUN 1 说"我住在上海"，RUN 2 说"我搬到北京了，更新一下"。观察模型能不能找到旧记忆的 id 并完成覆写，而不是新旧并存。

2. **启动时注入"最近记忆"**：在 Runtime Context 分节里注入最近 3 条记忆（`memory.json` 数组的尾部），与按需检索并存。对比混合策略与纯检索策略在 RUN 2 的表现，想想哪类记忆适合常驻、哪类只适合检索。

3. **子代理与记忆**：第九章的子代理上下文是彻底隔离的。让 researcher 子代理也能用 `search_memory`（把工具加进它的 `tools` 子集），派它去研究"根据我的饮食禁忌推荐餐厅"。思考：记忆共享打破了子代理的隔离性，这笔交换什么时候值得？
