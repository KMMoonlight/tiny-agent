# 11 · Exception Handle and Retry：异常处理与重试

前十章搭出来的 Agent，错误处理是**不对称**的：工具执行失败，早在第二章就被 `ToolRegistry.execute` 包成失败的 Observation 喂回给模型，模型读到原因后自己换条路。但 **LLM 请求本身一失败，整个 run 直接崩**，`llm.chat` 抛出的异常沿着调用栈一路穿透 `agent.ts` 的循环，进程带着一条裸的 stack trace 死掉。网络抖一下、被限流 429、服务端 502，跑到一半的 run 就没了。

本章把这块补齐：**错误分类 + 结构化错误 + 指数退避重试**。改动集中在 `llm.ts` 和一个新的 `retry.ts`，`agent.ts` 一行没动。

## 关键认识：先分类，再谈重试

到这一章，Agent 身上的错误可以分成三类，每一类的归宿完全不同：

| 错误 | 归宿 | 谁来处理 |
|---|---|---|
| 工具执行错误 | 包成 Observation 进消息历史 | 模型，只有它能换条路 |
| LLM 请求错误（网络、429、5xx） | 本章：静默重试 | 基础设施，模型不需要知道 |
| 终止性错误（maxSteps 超限、空 choices） | 直接 throw | 调用方 |

表格第一行和第二行的对照是本章最重要的一课：**工具错误必须进消息历史让模型看到**，因为模型读到"参数非法"会修正参数重新调用。**网络抖动没有任何换条路可言**：同一批消息、同一个模型，问题不在推理，在传输。把它也塞进上下文只会污染消息历史。

## 结构化错误：`LLMError`

重试的前提是回答一个问题：**这个错误值不值得重试？** 不是每个失败都有第二次机会：

- **可重试**：网络故障（连接被拒、DNS 失败、超时）、429（限流）、408、5xx（服务端故障），它们都是瞬时故障，再过一次请求往往就成功了
- **不可重试**：401（认证失败）、400（参数非法）、404（模型名写错），请求本身有问题，重试 100 次也不会成功，只会浪费时间并撞上更严的限流

`llm.ts` 的做法是把 `fetch` 抛出的所有异常统一包成 `LLMError`，携带两个字段：`status`（HTTP 状态码）和 `retryable`（布尔值）。上层，也就是本章的重试层，**只看这两个字段做决策，不再解析错误消息字符串**。错误消息是给人看的，错误分类是给程序用的，混在一起写出的重试代码迟早要在字符串里 `includes("rate limit")`。

## 重试放在哪一层：装饰器

确定了"值得重试"，下一个问题是"重试代码写在哪"。三个候选位置：

1. **写进 `agent.ts` 的循环**：最直接的直觉，但第八章的压缩和第九章的子代理各自也调用 `llm.chat`，同样的重试逻辑要写三遍，或循环要为两件事负责
2. **写进 `OpenAICompatibleClient` 内部**：单文件变胖，"发一次请求"和"反复试到成功"是两种职责，混在一个类里
3. **再包一层装饰器（本章的做法）**：`RetryingLLMClient` 也实现 `LLMClient` 接口，内部持有真正的 client，失败且可重试时按策略重发

第五章把 LLM 抽象成接口、靠构造函数注入，在这里兑现了红利：**Agent、压缩、子代理全都面向 `LLMClient` 编程**，装饰器在构造时替换一次，三个调用方同时获得重试能力，一行业务代码都不用改。这也是系列里反复出现的同一个结构：扩展发生在边界上，不在循环里。

```ts
const llm = new RetryingLLMClient(
  new OpenAICompatibleClient(baseURL, apiKey, model),
  { maxRetries: 3, baseDelayMs: 1_000, maxDelayMs: 8_000 },
);
```

## 指数退避：给故障方留恢复时间

重试的反面教材是"立即重试"：服务器刚说"太忙了"（429），立刻再压一个请求上去，只会让它更忙。正确做法是每失败一次就把等待时间翻倍：

```
1s → 2s → 4s →（封顶 maxDelayMs）
```

`retry.ts` 的实现只有三个配置：`maxRetries`（最多额外重试几次）、`baseDelayMs`（退避起点）、`maxDelayMs`（退避上限）。循环里两条终止条件：错误不可重试时立刻抛出（401 重试没有意义），重试次数耗尽时把错误原样抛给上层。**重试不承诺永不失败，它能做的是给瞬时故障几次机会，然后体面地失败。**

## `onRetry`：重试必须可见

重试是双刃剑。它把瞬时故障变成慢一点的请求，这通常是对的。但如果失败是持续的，比如配置写错、服务挂了，重试只是把崩溃延迟几秒，外加几次无效请求。一个不打印任何日志的重试层，在出问题时会变成最难排查的沉默延迟。所以 `RetryConfig` 带一个 `onRetry` 回调，把每次重试变成日志里的一条事件，观测性和前几章的 hooks 是同一个哲学。

## 本章的演示任务

`main.ts` 跑两次 run：

```
RUN 1：现在上海时间几点？算一下从现在到今天午夜还有多少分钟？
RUN 2：把一个 Agent 指向 http://127.0.0.1:9（不可达的地址）
```

RUN 1 是一次正常任务（`current_time` + `calculator`），重试层静默待命。RUN 2 是故障演示：连接被拒 → 错误可重试 → 按退避策略重试两次 → 重试耗尽 → `agent.run` 抛出一个干净的 `LLMError`，被 `main` 捕获打印，**程序没有崩**。

## 运行

```bash
npx tsx 11ExceptionRetry/main.ts
```

观察 RUN 2 的输出：两次 `[retry]` 日志（500ms → 1000ms 退避）之后，run 带着清晰的错误消息结束。值得做的对照实验：

- **把 `.env` 里的 `LLM_API_KEY` 改成错的再跑 RUN 1**：401 不可重试，一条 `[retry]` 日志都不会出现，体会快速失败的价值
- **把 `maxRetries` 改成 0**：装饰器退化为透明包装，故障直接穿透
- **RUN 1 跑到一半拔掉网线**：观察重试与最终失败；再插回网线重跑，体会瞬时故障与持续故障的区别

## 它的边界

- **没有 jitter（随机抖动）**，指数退避的教科书版本还要乘一个随机系数（如 `delay * (0.5 + Math.random())`）：一群客户端同时收到 429 时，纯指数退避会让它们在同一时刻一起重试，制造第二波冲击。在真实的分布式系统里，jitter 是必需项，不是优化项。
- **没有解析 `Retry-After` 响应头**，规范的限流响应会带这个头，直接告诉客户端过多久再来，比本地计算的退避更准确。
- **只有请求级重试，没有 run 级恢复**，重试耗尽后整个 run 作废，跑到一半的消息历史随之丢弃。真实系统会把消息历史落盘，支持从断点继续。
- **终止性错误仍然是裸的 throw**，maxSteps 超限、空 choices 在分类上正确地直接失败，但真实系统往往需要降级，比如步数耗尽时把当前进度作为部分答案返回，而不是让调用方面对一个异常。

## 动手练习

1. **尊重 `Retry-After`**：给 `LLMError` 加一个 `retryAfterMs` 字段，在 `llm.ts` 里从 429 响应头解析 `Retry-After`；`RetryingLLMClient` 计算退避时间时优先采用它。对比两种策略下重试的礼貌程度。

2. **加 jitter**：把退避时间改成 `Math.min(base * 2 ** attempt, max) * (0.5 + Math.random())`，打印几次退避序列，观察随机化如何把同时失败的客户端打散。

3. **run 级断点续跑**：给 `agent.ts` 加消息历史落盘（每步结束把 `messages` 写到文件），崩溃后支持 `--resume` 从上次断点继续。注意第八章学到的约束：续跑加载的历史不能以未配对的 tool 消息开头。完成后想想：哪些故障值得断点续跑，哪些直接重跑更便宜？
